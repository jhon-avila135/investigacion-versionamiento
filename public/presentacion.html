1. Contexto y caso práctico

Caso práctico

  • Sitio estático con la investigación y esta presentación.
  • GitHub como repositorio principal; GitLab como réplica.
  • Cada cambio entra por pull request y se valida antes de llegar a main.
  • Cada plataforma despliega su copia con su propio pipeline.
  • El pie de página muestra la plataforma, el commit y la fecha de publicación.

3. Despliegue en cada plataforma

GitHub Actions

permissions:
  pages: write
  id-token: write              # token OIDC temporal
jobs:
  validate:
    steps:
      - run: npx --yes html-validate "public/**/*.html"
  deploy:
    needs: validate            # sin validación no hay despliegue
    environment: github-pages
    steps:
      - uses: actions/upload-pages-artifact@v3
      - uses: actions/deploy-pages@v4

3. Despliegue en cada plataforma

GitLab CI

stages: [validate, deploy]
validate:
  image: node:22-alpine
  script:
    - npx --yes html-validate "public/**/*.html"
pages:                         # el nombre activa GitLab Pages
  stage: deploy
  artifacts:
    paths: [public]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

5. Variables, reversión y comandos

Reversión y comandos

git remote add gitlab URL         # segundo remoto
git push gitlab main              # réplica y despliegue en GitLab
git rebase main                   # actualizar la rama antes del PR
git push --force-with-lease       # solo la rama propia
git revert HEAD                   # reversión sin reescribir historial
git tag -a v1.0.0 -m "entrega"    # versión de entrega

7. Resultados, hallazgos y conclusiones

Hallazgos

  • La validación omitía la accesibilidad hasta probarla con un caso real.
  • El commit publicado tras un merge difiere del commit local.
  • GitLab no admite un proyecto público dentro de un grupo privado.
  • GitLab Pages sirvió por unos segundos versiones distintas tras cada despliegue.
  • Los pipelines no son compatibles entre plataformas.

7. Resultados, hallazgos y conclusiones

Criterios de selección

GitHub

  • Proyectos académicos y de código abierto
  • Beneficios para estudiantes
  • Ecosistema de integraciones

GitLab

  • Instalación en servidores propios
  • Ciclo completo en una herramienta
  • Grupos con herencia

7. Resultados, hallazgos y conclusiones

Conclusiones

  1. Ambas plataformas resuelven las mismas necesidades con modelos distintos.
  2. Una regla de protección solo es efectiva si se verifica.
  3. El correo institucional tiene más impacto en GitHub; en GitLab depende de la universidad.
