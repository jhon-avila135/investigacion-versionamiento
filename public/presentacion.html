01 · El problema

¿Cuál es la versión que funciona?

02 · Fundamentos

Git no es GitHub ni GitLab

Herramienta

Git

Control de versiones distribuido, creado por Linus Torvalds en 2005. Vive en tu computadora con el historial completo.

Plataforma

GitHub

Aloja repositorios y suma pull requests, Actions, Pages y Copilot. De Microsoft desde 2018.

Plataforma DevSecOps

GitLab

Una sola aplicación para todo el ciclo. Open core: se puede instalar en servidores propios.

Git es el motor; GitHub y GitLab son los talleres construidos alrededor de él.

02 · Fundamentos

Los comandos de todos los días

git clone URL                       # copiar un repositorio
git status                          # ver qué cambió
git add public/                     # preparar cambios
git commit -m "feat: sección reglas" # guardar una versión
git switch -c feat/reglas           # crear rama y moverse
git push -u origin feat/reglas      # enviar al remoto
git pull origin main                # traer e integrar
git remote add gitlab URL           # segundo remoto
git revert HEAD                     # deshacer sin reescribir
git tag -a v1.0.0 -m "estable"      # marcar una versión

02 · Fundamentos

Tres estrategias de ramas

Simple

GitHub Flow

main siempre desplegable y ramas cortas que vuelven por pull request. La usamos en este proyecto.

Planificada

GitFlow

main, develop, feature, release y hotfix. Para versiones fechadas.

Avanzada

Trunk-based

Todos integran a main varias veces al día, con feature flags.

02 · Fundamentos

Versionar también es comunicar

v2.4.1

MAYOR rompe compatibilidad · MENOR agrega funciones · PARCHE corrige errores (SemVer 2.0.0).

feat(auth): inicio de sesión  # menor
feat!: cambia la API de pagos # mayor
ci: agrega pipeline de Pages

03 · GitHub frente a GitLab

Misma base: Git. Distinta filosofía.

GitHub apuesta por la comunidad y un ecosistema de integraciones. GitLab apuesta por una sola plataforma que cubre todo el ciclo DevSecOps, en la nube o en tus propios servidores.

04 · Reglas

Cómo cada plataforma protege main

GitHub · Rulesets
  • PR obligatorio con aprobaciones
  • Status checks requeridos
  • CODEOWNERS
  • Bloqueo de force push
GitLab · Ramas protegidas
  • Push y merge por rol
  • Pipelines must succeed
  • Tags protegidos
  • Variables protegidas

Regla común: nada entra a main sin revisión y sin el CI en verde.

04 · Variables

Configuración fuera del código

GitHub Actions

secrets (cifrados), vars (configuración) y environments con aprobación.

${{ vars.ENTORNO }}
${{ secrets.TOKEN }}
$GITHUB_SHA   # predefinida
GitLab CI/CD

Variables masked, protected y de tipo File, por proyecto, grupo o entorno.

$ENTORNO
$CI_COMMIT_SHORT_SHA  # predefinida
$CI_DEFAULT_BRANCH    # predefinida

05 · Nuestro pipeline en GitHub

.github/workflows/deploy.yml

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npx --yes html-validate "public/**/*.html"
  deploy:
    needs: validate              # sin validación no hay despliegue
    environment: github-pages
    steps:
      - run: sed -i "s|__VERSION__|${GITHUB_SHA::7}|g" public/*.html
      - uses: actions/upload-pages-artifact@v3
      - uses: actions/deploy-pages@v4   # token OIDC, sin contraseñas

05 · Nuestro pipeline en GitLab

.gitlab-ci.yml

stages: [validate, deploy]

validate:
  image: node:22-alpine
  script:
    - npx --yes html-validate "public/**/*.html"

pages:                       # el nombre "pages" activa GitLab Pages
  stage: deploy
  script:
    - sed -i "s|__VERSION__|$CI_COMMIT_SHORT_SHA|g" public/*.html
  artifacts:
    paths: [public]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

05 · Demo de reglas

Rompimos el HTML a propósito

Un pull request quitó el texto alternativo de una imagen. El job validate falló y GitHub bloqueó el botón de merge.

Al corregirlo, el check pasó a verde y se pudo fusionar. Así funciona la integración continua: el error se detecta antes de llegar a producción, no después.

06 · Decisión

¿Cuál elegir?

GitHub si…
  • Portafolio o código abierto
  • Comunidad y Marketplace
  • Copilot integrado
  • Muchos minutos de CI gratis
GitLab si…
  • Servidores propios (banca, salud, gobierno)
  • Todo DevSecOps en una herramienta
  • Runners propios
  • Seguridad integrada

06 · Pensamiento crítico

Limitaciones y riesgos

  • Curva de aprendizaje: conflictos y rebase sin reglas claras generan errores costosos.
  • Archivos grandes: videos, modelos o datasets necesitan Git LFS.
  • Dependencia del proveedor: el código migra fácil; los pipelines no. Lo vivimos al escribir dos.
  • Cadena de suministro: acciones de terceros y secretos olvidados en el historial.

06 · Para llevar

Buenas prácticas

  • Commits pequeños y convencionales
  • Una rama por tarea, de vida corta
  • PR o MR con revisión
  • main protegida y CI obligatorio
  • .gitignore desde el primer commit
  • Secretos en el gestor, nunca en el código
  • Versiones con SemVer
  • README siempre al día

06 · Conclusiones

Lo que queremos que recuerden

  1. Git es la herramienta; GitHub y GitLab son plataformas que suman colaboración, automatización y gobierno.
  2. La diferencia real es de filosofía: ecosistema frente a plataforma única.
  3. Lo profesional no es elegir una: es proteger main, automatizar el despliegue y medir.
