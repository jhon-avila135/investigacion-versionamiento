02 · Despliegue en GitHub

.github/workflows/deploy.yml

permissions:
  pages: write
  id-token: write               # token OIDC: cero contraseñas guardadas
jobs:
  validate:
    steps:
      - run: npx --yes html-validate "public/**/*.html"
  deploy:
    needs: validate             # sin validación no hay despliegue
    environment: github-pages   # historial de despliegues
    steps:
      - run: sed -i "s|__VERSION__|${GITHUB_SHA::7}|g" public/*.html
      - uses: actions/upload-pages-artifact@v3
      - uses: actions/deploy-pages@v4

02 · Despliegue en GitLab

.gitlab-ci.yml

stages: [validate, deploy]
validate:
  image: node:22-alpine
  script:
    - npx --yes html-validate "public/**/*.html"
pages:                          # el nombre activa GitLab Pages
  stage: deploy
  script:
    - sed -i "s|__VERSION__|$CI_COMMIT_SHORT_SHA|g" public/*.html
  artifacts:
    paths: [public]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

03 · Reglas

Cómo cada uno protege main

GitHub · Ruleset proteger-main
  • PR obligatorio
  • Check validate obligatorio
  • Sin force push ni borrado
  • Sin excepciones, ni para el dueño
GitLab · Rama protegida
  • Push y merge solo Maintainers
  • Pipelines must succeed (gratis)
  • Aprobaciones obligatorias: Premium
  • CODEOWNERS: Premium

En GitHub Free estas reglas solo aplican a repos públicos; en privados se necesita Pro, que viene con GitHub Education.

03 · Demo

Rompimos el HTML a propósito

PR #3: quitamos el texto alternativo del QR. validate falló y GitHub bloqueó el merge.

Y antes descubrimos algo mejor: el validador no lo detectaba. El preset standard no revisa accesibilidad; lo corregimos en el PR #2. La regla solo protege si alguien la prueba.

04 · Gestión de despliegues

Rollback y comandos que usamos

git remote add gitlab URL           # segundo destino
git push gitlab main                # dispara GitLab CI
git config credential.https://github.com.username USUARIO
git rebase main                     # rama al día antes del PR
git push --force-with-lease         # solo tu rama; en main está bloqueado
git revert HEAD                     # rollback sin reescribir historia
git tag -a v1.0.0 -m "entrega"      # versión que se entrega

06 · Hallazgos

Lo que no esperábamos

  • El validador estaba a medias: una imagen sin alt pasaba.
  • El commit publicado no es el de tu PC: el merge crea otro.
  • Un proyecto público no cabe en un grupo privado en GitLab.
  • La PC tenía guardada otra cuenta: hay que fijar el usuario por repositorio.
  • Los pipelines no se migran: escribimos dos. Esa es la verdadera dependencia del proveedor.

06 · Decisión

¿Cuál elegir?

GitHub si…
  • Proyecto de estudiantes o código abierto
  • Portafolio y comunidad
  • Se aprovecha el Student Pack
GitLab si…
  • Se instala en servidores propios
  • Todo el ciclo en una herramienta
  • La universidad tiene la licencia educativa

Conclusiones

Lo que queremos que recuerden

  1. GitHub y GitLab hacen lo mismo con modelos distintos: eventos y ecosistema frente a etapas y plataforma única.
  2. Una regla solo protege si se prueba: nuestro validador fallaba en silencio.
  3. El correo institucional pesa más en GitHub; en GitLab depende de la universidad.
