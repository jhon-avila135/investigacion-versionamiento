1 · El problema

¿Cuál es la versión que funciona?

proyecto_final.zip, proyecto_final_v2.zip, proyecto_final_FINAL_ahora_si.zip. Sin control de versiones no hay historial, no se sabe quién cambió qué y no existe una forma segura de que varias personas trabajen sobre el mismo código.

2 · Fundamentos

Git no es lo mismo que GitHub ni que GitLab

Git (herramienta)
Sistema de control de versiones distribuido, creado por Linus Torvalds en 2005 para el kernel de Linux. Vive en la computadora y cada copia tiene el historial completo.
GitHub (plataforma)
Servicio que aloja repositorios Git y agrega colaboración: pull requests, issues, Actions para CI/CD, Pages y Copilot. Es de Microsoft desde 2018.
GitLab (plataforma DevSecOps)
Una sola aplicación para todo el ciclo: código, CI/CD, seguridad, registro de contenedores y despliegue. Su modelo es open core, así que se puede instalar en servidores propios.

Git es el motor; GitHub y GitLab son los talleres construidos alrededor de él.

4 · Fundamentos

Tres estrategias de ramas

Simple

GitHub Flow

Una rama main siempre desplegable y ramas cortas por tarea que vuelven por pull request. Es la que usamos en este proyecto.

Planificada

GitFlow

Ramas main y develop, más feature, release y hotfix. Más control y más ceremonia; sirve para software con versiones fechadas.

Avanzada

Trunk-based

Todos integran a main varias veces al día y lo incompleto se oculta con feature flags. Requiere pruebas automáticas fuertes.

5 · Fundamentos

Versionar también es comunicar

Semantic Versioning 2.0.0: en v2.4.1, el 2 es la versión MAYOR (rompe compatibilidad), el 4 la MENOR (agrega funciones compatibles) y el 1 el PARCHE (corrige errores).

Conventional Commits 1.0.0: los mensajes llevan un tipo. fix sube el parche, feat sube la menor y feat! (cambio incompatible) sube la mayor. Así el número de versión se puede calcular a partir del historial.

fix: valida correo vacío
feat(auth): inicio de sesión
docs: actualiza README
ci: agrega pipeline de despliegue

7 · Despliegue

Cómo desplegar en cada uno

Un pipeline es una lista de comandos que una máquina limpia (runner) ejecuta cada vez que pasa algo en el repositorio. CI (integración continua) valida cada cambio antes de unirlo a main; CD (despliegue continuo) publica automáticamente lo que pasó la validación.

GitHub Actions → Pages

Acciones explícitas

Un workflow en .github/workflows con dos jobs: validate y deploy. deploy depende de validate (needs) y usa las acciones oficiales configure-pages, upload-pages-artifact y deploy-pages. No guarda contraseñas: usa un token OIDC temporal por ejecución.

GitLab CI → Pages

Convención

Un .gitlab-ci.yml con stages validate y deploy. Cada job corre dentro de una imagen Docker. Basta con que un job se llame pages y deje la carpeta public como artefacto para que GitLab la publique.

Los dos pipelines completos están en el repositorio y en la presentación.

8 · Reglas

Cómo cada plataforma protege main

GitHub

Rulesets y branch protection

PR obligatorio con N aprobaciones; status checks requeridos (el CI debe pasar); CODEOWNERS; bloqueo de force push y de borrado; commits firmados e historial lineal. Si hay varios rulesets, gana la regla más estricta.

GitLab

Ramas protegidas

Quién puede hacer push o merge, por rol; "Pipelines must succeed" antes de fusionar; reglas de aprobación de MR (obligatorias en Premium); tags protegidos para releases; variables protegidas que solo existen en ramas protegidas.

Regla común: nada entra a main sin revisión y sin el CI en verde.

9 · Variables

Configuración fuera del código

GitHub Actions

Secrets, variables y environments

Niveles de organización, repositorio y environment. Los secrets se cifran y se ocultan en los logs; las variables son configuración no sensible. Los environments pueden pedir aprobación antes de desplegar.

GitLab CI/CD

Masked, protected y File

Niveles de instancia, grupo y proyecto. Masked oculta el valor en los logs; Protected solo la entrega a ramas o tags protegidos; el tipo File la escribe en un archivo. Se pueden limitar por entorno.

En nuestro proyecto el pie de página se llena durante el despliegue con una variable predefinida (el commit: GITHUB_SHA o CI_COMMIT_SHORT_SHA) y con una variable propia, ENTORNO, configurada en cada plataforma. Un secreto nunca va en el repositorio; si se filtró, se revoca.

11 · Ejemplo práctico

Este mismo sitio

El ejemplo práctico es el sitio que estás leyendo. GitHub es la fuente de verdad: cada cambio se hace en una rama, se propone con un pull request y solo se fusiona si el job validate está en verde. Después, la rama main se envía también a GitLab, que la despliega con su propio pipeline.

Para demostrar las reglas, abrimos a propósito un pull request que quita el texto alternativo de una imagen: la validación falla y GitHub bloquea la fusión. Las capturas y las mediciones están en la presentación y en la página de inicio.

12 · Decisión

¿Cuál elegir?

Elige GitHub si…

construyes portafolio o código abierto, quieres la comunidad y el Marketplace más grandes, te sirve Copilot integrado o necesitas muchos minutos de CI gratis.

Elige GitLab si…

debes instalarlo en servidores propios (banca, salud, gobierno), quieres todo el ciclo DevSecOps en una herramienta o necesitas runners propios y pipelines complejos.

No es excluyente: GitLab puede espejar repositorios y ejecutar CI para código alojado en GitHub, que es justo lo que hacemos aquí.

13 · Pensamiento crítico

Limitaciones y riesgos

Curva de aprendizaje
Conflictos, rebase y reescritura de historia generan errores costosos si el equipo no tiene reglas claras.
Archivos grandes y binarios
Git versiona muy bien el texto, pero no videos, modelos o datasets; para eso se necesita Git LFS u otro almacenamiento.
Dependencia del proveedor
El código migra fácil; los pipelines no. Un workflow de Actions no corre en GitLab sin reescribirse, y los planes gratuitos cambian.
Cadena de suministro
Acciones de terceros y secretos olvidados en el historial son hoy una de las vías de ataque más comunes.
