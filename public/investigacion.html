1.Diferencias de modelo

Ambas plataformas alojan repositorios Git, pero parten de enfoques distintos. GitHub se organiza alrededor de una comunidad y de un ecosistema de integraciones; la mayoría de las funciones se componen con piezas reutilizables. GitLab se presenta como una aplicación única para todo el ciclo DevSecOps y puede instalarse en servidores propios.

Tabla 1. Diferencias técnicas relevantes para el proyecto.
AspectoGitHubGitLab
Modelo de CI/CDBasado en eventos (push, pull request, horario o ejecución manual). Los pasos se reutilizan como acciones.Basado en etapas que se ejecutan en orden. La reutilización se hace con include, extends y plantillas.
Entorno de ejecuciónSe elige la máquina virtual (runs-on).Se elige la imagen del contenedor (image).
Publicación de un sitioPasos explícitos con acciones oficiales.Convención: un job llamado pages que entrega la carpeta public.
OrganizaciónOrganizaciones y equipos, sin niveles intermedios.Grupos y subgrupos; permisos y variables se heredan.
Instalación propiaEnterprise Server, con licencia de pago.Community Edition, gratuita y de código abierto.
Primer uso de CIDisponible al crear la cuenta.Requiere verificar la identidad para usar los runners compartidos.

2.Despliegue en cada plataforma

2.1GitHub Actions hacia GitHub Pages

El workflow tiene dos jobs. validate revisa el HTML; deploy depende de él y solo se ejecuta en main. El sitio se empaqueta como artefacto y se publica en el entorno github-pages, que conserva el historial de despliegues. No se almacena ninguna credencial: el permiso id-token: write habilita la emisión de un token OIDC temporal en cada ejecución.

deploy:
  needs: validate
  environment: github-pages
  steps:
    - uses: actions/upload-pages-artifact@v3
    - uses: actions/deploy-pages@v4

2.2GitLab CI hacia GitLab Pages

El pipeline tiene dos etapas. validate se ejecuta en un contenedor de Node; pages reemplaza las variables del HTML y entrega la carpeta public. GitLab reconoce el nombre del job y publica el sitio; durante la ejecución agrega por su cuenta el job pages:deploy. La regla if restringe la publicación a la rama principal.

pages:
  stage: deploy
  artifacts:
    paths: [public]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

Los archivos completos están en el workflow de GitHub y en el archivo de GitLab CI.

En GitHub Free, las ramas protegidas, los revisores obligatorios y CODEOWNERS solo se aplican a repositorios públicos; en repositorios privados requieren GitHub Pro, plan incluido en GitHub Education.

En el proyecto se configuró la regla proteger-main sin lista de excepciones, de modo que ni el propietario del repositorio puede omitirla.

4.Variables y gestión de despliegues

Tabla 3. Gestión de variables y despliegues.
AspectoGitHubGitLab
NivelesOrganización, repositorio y entornoInstancia, grupo (heredable) y proyecto
Datos sensiblessecrets, cifrados y ocultos en los registrosVariables masked o masked and hidden
Configuración no sensiblevarsVariables visibles o de tipo archivo
Protección de producciónEntornos con revisores y ramas permitidasVariables protegidas: solo existen en ramas o etiquetas protegidas
Variables predefinidas usadasGITHUB_SHACI_COMMIT_SHORT_SHA, CI_DEFAULT_BRANCH
Despliegues simultáneosconcurrencyresource_group

El pie de página del sitio se completa durante el despliegue: el commit proviene de una variable predefinida y el entorno, de la variable propia ENTORNO. En GitLab esta variable es protegida, por lo que un pipeline ejecutado en una rama de prueba no la recibe. Es el mismo mecanismo que se usa para que una rama sin revisión no acceda a credenciales de producción.

La reversión de un cambio publicado se hace con git revert: se crea un commit que deshace el anterior y el mismo pipeline publica la corrección. GitHub ofrece además la opción Revert en cada pull request fusionado.

6.Cuentas educativas

El grupo usa cuentas con correo institucional en ambas plataformas. Los beneficios difieren en un punto central: GitHub los otorga al estudiante; GitLab, a la institución.

Reglas en repositorios privadosNo disponiblesRamas protegidas, revisores obligatorios, CODEOWNERS y wikis

AspectoGitLab FreeGitLab for Education

En consecuencia, el correo institucional mejora de inmediato las condiciones en GitHub, mientras que en GitLab la cuenta del estudiante funciona como una cuenta Free; acceder a Ultimate depende de una solicitud de la universidad. En ambos casos los beneficios están sujetos a renovación, y su pérdida afecta a los proyectos que dependan de funciones de pago.

7.Hallazgos de la implementación

Validación incompleta
El preset html-validate:standard no revisa accesibilidad: una imagen sin texto alternativo aprobaba la validación. Se detectó al probar la regla y se corrigió con el preset a11y (PR #2).
Commit publicado distinto del local
Al fusionar un pull request, GitHub crea un commit de merge con otro identificador. La medición se basa por ello en la versión publicada, no en el commit local.
Visibilidad heredada en GitLab
Un proyecto público no puede pertenecer a un grupo privado; fue necesario cambiar la visibilidad del grupo.
Propagación de GitLab Pages
Durante algunos segundos posteriores a un despliegue, el sitio respondió con la versión nueva o la anterior según el servidor. La medición se ajustó para exigir la versión esperada en tres lecturas consecutivas y se descartaron dos registros inválidos.
Credenciales en el equipo
El administrador de credenciales tenía guardada una cuenta personal. Sin fijar el usuario por repositorio, los cambios se habrían enviado con otra identidad.
Dependencia del proveedor
El código se replica con un push, pero los pipelines no son compatibles entre plataformas y deben escribirse por separado.

Las plataformas no son excluyentes. En este proyecto GitHub es el repositorio principal y GitLab, un segundo destino de despliegue.

9.Conclusiones

  1. GitHub y GitLab resuelven las mismas necesidades con modelos distintos: eventos y ecosistema frente a etapas y plataforma integrada.
  2. Una regla de protección solo es efectiva si se verifica: la validación del proyecto omitía la accesibilidad hasta que se probó con un caso real.
  3. El correo institucional tiene más impacto en GitHub; en GitLab, el beneficio depende de una gestión de la universidad.
