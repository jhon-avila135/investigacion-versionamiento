Investigación

GitHub frente a GitLab

No nos quedamos en "uno tiene PR y el otro MR". Configuramos las dos plataformas para desplegar el mismo sitio y aquí contamos qué cambia de verdad: cómo despliegan, cómo protegen la rama principal, cómo manejan variables y qué nos da a cada uno el correo institucional.

1 · Diferencias

La diferencia real es de modelo, no de botones

GitHub es una plataforma alrededor de una comunidad y un ecosistema: casi todo se arma combinando piezas (acciones del Marketplace, apps, integraciones). GitLab es una sola aplicación que intenta cubrir todo el ciclo DevSecOps y que además se puede instalar en servidores propios. Eso se nota en cada detalle técnico:

AspectoGitHubGitLab
Modelo de CI/CDPor eventos: un workflow reacciona a push, PR, horario o a mano. Los pasos se reutilizan como acciones (uses: actions/checkout@v4).Por etapas: stages que corren en orden y jobs dentro de cada etapa. Se reutiliza con include, extends y plantillas.
Dónde corre cada jobSe elige la máquina (runs-on: ubuntu-latest).Se elige el contenedor (image: node:22-alpine) sobre un runner compartido o propio.
Publicar un sitioPasos explícitos: subir el artefacto y desplegarlo con acciones oficiales.Convención: un job llamado pages que deje la carpeta public como artefacto.
OrganizaciónOrganizaciones y equipos, sin niveles intermedios.Grupos y subgrupos; permisos y variables se heredan hacia abajo.
Instalación propiaEnterprise Server, solo de pago.Community Edition gratuita y de código abierto.
Antes del primer pipelineFunciona de inmediato.En GitLab.com hay que verificar la identidad (teléfono o tarjeta) para usar los runners compartidos; es una medida contra el abuso de cómputo.

2 · Despliegue

Cómo se despliega en cada uno

GitHub Actions → GitHub Pages

Dos jobs y un entorno

validate revisa el HTML; deploy depende de él (needs) y solo corre en main. El sitio se empaqueta con upload-pages-artifact y se publica con deploy-pages en el entorno github-pages, que guarda el historial de despliegues. No hay ninguna contraseña guardada: el permiso id-token: write hace que GitHub emita un token OIDC temporal para cada ejecución.

GitLab CI → GitLab Pages

Dos stages y una convención

validate corre en un contenedor de Node; pages corre en Alpine, reemplaza las variables en el HTML y deja public como artefacto. GitLab detecta el nombre del job y publica solo. La regla if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH evita que una rama cualquiera publique.

En los dos casos el pipeline es la única forma de llegar a producción: nadie sube archivos a mano. Los archivos completos están en el workflow de GitHub y en el .gitlab-ci.yml.

3 · Reglas

Cómo protege cada uno la rama principal

GitHub · Rulesets

Lo que activamos

Un ruleset llamado proteger-main: PR obligatorio, el check validate obligatorio, bloqueo de force push y de borrado. Sin lista de excepciones, así que ni el dueño del repositorio puede saltárselo. Los rulesets se pueden apilar y gana la regla más estricta.

GitLab · Ramas protegidas

Lo que trae y lo que cuesta

main nace protegida: solo Maintainers hacen push o merge y no se permite force push. "Pipelines must succeed" es gratis; las reglas de aprobación obligatorias, CODEOWNERS y push rules son de Premium.

Detalle de planes que casi nadie menciona: en GitHub Free las ramas protegidas, los revisores obligatorios y CODEOWNERS funcionan solo en repositorios públicos. Para usarlos en repositorios privados se necesita GitHub Pro, que es justo lo que da GitHub Education a los estudiantes verificados.

4 · Variables

Variables y gestión de despliegues

TemaGitHubGitLab
NivelesOrganización, repositorio y environmentInstancia, grupo (heredable a subgrupos) y proyecto
Datos sensiblessecrets: cifrados y ocultos en los logsMasked, o Masked and hidden si tampoco se deben ver en la configuración
Configuraciónvars.NOMBRE, visiblesVariables visibles; también de tipo File
Proteger producciónEnvironments con revisores obligatorios y ramas permitidasProtected: la variable solo existe en ramas o tags protegidos
Predefinidas que usamosGITHUB_SHACI_COMMIT_SHORT_SHA, CI_DEFAULT_BRANCH
Despliegues simultáneosconcurrency: group: pagesresource_group

En nuestro sitio, el pie de página se llena durante el despliegue: el commit sale de una variable predefinida y el entorno, de una variable propia llamada ENTORNO. En GitLab la marcamos como protegida: si alguien corre un pipeline en una rama de prueba, ENTORNO no existe ahí. Así se evita en la vida real que una rama cualquiera vea credenciales de producción.

Rollback: volver atrás no es "subir la versión anterior a mano". Se hace git revert del cambio y el mismo pipeline publica la corrección. GitHub incluso tiene un botón Revert en cada PR fusionado.

5 · Comandos

Los comandos que de verdad usamos

No ponemos aquí git add ni git commit, que todos conocen. Estos son los que necesitamos para trabajar con dos plataformas y con main protegida:

ComandoPara qué lo usamos
git remote add gitlab URLTener dos remotos: origin (GitHub) y gitlab.
git push gitlab mainLlevar main a GitLab después de fusionar en GitHub; eso dispara su pipeline.
git config credential.https://github.com.username USUARIOObligar a que este repositorio use la cuenta institucional y no otra guardada en la PC.
git switch -c fix/prueba-validacionUna rama por tarea; main no se toca directamente.
git rebase mainPoner una rama al día con main antes de abrir el PR.
git push --force-with-leaseReescribir solo tu rama después del rebase, sin pisar trabajo ajeno. En main está bloqueado.
git revert HEADDeshacer un cambio publicado sin reescribir la historia.
git tag -a v1.0.0 -m "..."Marcar la versión que se entrega; se sube a los dos remotos.
git log --oneline --graphVer ramas y merges para explicar el flujo.

6 · Correo institucional

Cuenta educativa frente a cuenta normal

Usamos cuentas con el correo de la UCE en las dos plataformas, y descubrimos que el beneficio es muy distinto: GitHub le da beneficios al estudiante; GitLab se los da a la institución.

AspectoGitHub FreeGitHub con Education (estudiante)
Quién lo pideCualquieraEl estudiante, con correo académico verificado y un documento que pruebe la matrícula
PlanFreeBeneficios de GitHub Pro mientras dure la verificación
Reglas en repos privadosNo (solo públicos)Sí: ramas protegidas, revisores obligatorios, CODEOWNERS y wikis
Cómputo de ActionsCuota mensual de Free (los repos públicos no la consumen)Cuota mayor de Pro
Codespaces120 horas-núcleo al mes180 horas-núcleo al mes
CopilotPlan gratuito con límitesCopilot con funciones premium, gratis
ExtrasNingunoStudent Developer Pack: créditos de nube, dominios y herramientas de terceros
AspectoGitLab FreeGitLab for Education
Quién lo pideCualquieraSolo docentes o personal de la universidad, con el correo institucional. GitLab no entrega licencias a estudiantes.
PlanFreeUltimate con asientos ilimitados, por un año renovable
Minutos de CI400 al mes por grupo50 000 al mes
Almacenamiento10 GiB por proyecto (repositorio y LFS)Según la licencia Ultimate
Uso permitidoLibreSolo enseñanza e investigación no comercial; no para administrar la universidad

Qué significa para nosotros: en GitHub, el correo de la UCE nos da un plan mejor desde hoy. En GitLab, nuestra cuenta con correo institucional es una cuenta Free normal; para tener Ultimate, un docente tendría que solicitar la licencia para la universidad. Lo malo de los dos: los beneficios dependen de seguir verificado o de renovar cada año, y si se pierden, los proyectos que dependan de funciones de pago dejan de funcionar igual.

8 · Hallazgos

Lo que no esperábamos

El validador estaba configurado a medias
Al preparar la prueba del error, una imagen sin texto alternativo pasó la validación: el preset html-validate:standard no revisa accesibilidad. Lo descubrimos probando la regla, no leyendo. Lo corregimos con el preset a11y en el PR #2.
El commit que se publica no es el de tu PC
Al fusionar un PR, GitHub crea un commit de merge con otro identificador. Por eso nuestro script de medición no compara contra el commit local: espera a que cambie la versión publicada.
Un proyecto público no puede vivir en un grupo privado
En GitLab la visibilidad se hereda: tuvimos que hacer público el grupo antes de crear el proyecto público.
La PC guarda la cuenta equivocada
El administrador de credenciales tenía una cuenta personal guardada. Si no se fija el usuario por repositorio, los commits se suben con otra identidad.
GitLab Pages tarda en ponerse de acuerdo
Justo después de un despliegue, el sitio de GitLab respondió unos segundos con la versión nueva y otros con la anterior, según el servidor que atendía. Por eso nuestro script solo da por publicado un cambio cuando lee la versión esperada tres veces seguidas.
Los pipelines no se migran
El código pasa de una plataforma a otra con un push; los pipelines hay que escribirlos de nuevo. Esa es la dependencia del proveedor que más pesa.

9 · Decisión

Cuándo elegir cada uno

GitHub si…

el proyecto es de estudiantes o de código abierto, se quiere portafolio y comunidad, se aprovecha el Student Pack o se necesita el ecosistema de acciones.

GitLab si…

la organización debe instalarlo en sus servidores (banca, salud, gobierno), quiere todo el ciclo en una herramienta, necesita grupos con herencia o la universidad ya tiene la licencia educativa.

No es excluyente: nosotros usamos GitHub como fuente de verdad y GitLab como segundo destino de despliegue.
