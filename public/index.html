1.Resumen

Este proyecto compara GitHub y GitLab desde la práctica. Se construyó un sitio estático con la investigación del grupo y se configuró en ambas plataformas el mismo proceso: cada cambio entra por una rama y un pull request, pasa una validación automática y, si la aprueba, se publica sin intervención manual.

Sobre ese proceso se midió el tiempo que tarda un cambio en estar disponible en cada plataforma y se registraron las diferencias encontradas en despliegue, reglas, variables y planes educativos.

2.Objetivos

2.1Objetivo general

Comparar la gestión de versiones y el despliegue continuo en GitHub y GitLab mediante un caso práctico medible.

2.2Objetivos específicos

  • Implementar un pipeline de validación y despliegue en cada plataforma.
  • Proteger la rama principal y comprobar que la protección bloquea cambios inválidos.
  • Gestionar la configuración del despliegue con variables propias y predefinidas.
  • Medir el tiempo de entrega en ambas plataformas y documentar los resultados.

3.Arquitectura del despliegue

GitHub actúa como repositorio principal. La rama main se replica en GitLab y cada plataforma publica su propia copia del sitio con su propio pipeline.

El pie de cada página muestra la plataforma, el commit publicado, el entorno y la fecha. Esos datos los escribe el pipeline durante el despliegue a partir de variables, lo que permite comprobar qué versión está en línea.

5.Implementación

5.1Configuración

  1. Cuentas creadas con el correo institucional en GitHub, GitLab y Atlassian. En el repositorio local se fijó el usuario de cada plataforma para evitar el uso de credenciales personales guardadas en el equipo.
  2. Repositorio público en GitHub y proyecto público dentro del grupo grupo2-versionamiento-uce en GitLab. El grupo debió hacerse público, ya que GitLab no admite un proyecto público dentro de un grupo privado.
  3. Pipelines definidos en deploy.yml y .gitlab-ci.yml, con dos etapas: validación del HTML y publicación.
  4. Variable ENTORNO en ambas plataformas; en GitLab, configurada como protegida.
  5. Regla proteger-main: pull request obligatorio, check validate obligatorio, sin force push ni borrado de la rama y sin excepciones.
  6. En GitLab, verificación de identidad para habilitar los runners compartidos, URL sin dominio aleatorio y acceso público al sitio.

6.Resultados

Se midieron dos tiempos: la duración del pipeline, que informa cada plataforma, y el tiempo de entrega, desde la aprobación del cambio hasta que el sitio publicado muestra la nueva versión. El segundo corresponde a una de las métricas DORA (Forsgren, Humble y Kim, 2018).

Tabla 3. Tiempos medidos por plataforma.
PlataformaPipelinesDuración mediaMedicionesEntrega media
GitHub Pages635,5 s749,4 s
GitLab Pages247,5 s160 s

En GitHub, el tiempo de entrega varió entre 43 y 65 s (desviación estándar de 7,9 s). La muestra de GitLab todavía es insuficiente para comparar; la meta es reunir 20 despliegues por plataforma con las mediciones de todo el grupo.

Datos completos en mediciones.csv. Procedimiento en scripts/medir.sh.
